# Правила работы над AshBound

## ФАЙЛЫ И GIT — строгие правила, 25 сентября 2026, D-080. Приоритет над всеми правилами ниже

Причина: `.git` весит 786 МБ, из них 450 МБ — снимки проверок в `art/previews/`. Каждая задача добавляла десятки PNG ПК/S23, JSON-отчёты, PDF и HTML-галереи. Репозиторий растёт на сотни МБ в неделю, а контекст агентов уходит на чтение отчётов вместо кода. Если любое правило ниже (про снимки, протоколы, «сохранить в проекте», «справочник в Git») противоречит этому разделу — действует этот раздел.

### 1. В Git попадает только то, без чего проект не собирается или не воспроизводится

1. Код и сцены: `.gd`, `.tscn`, `.tres`, `.gdshader`, `project.godot`, `export_presets.cfg`, `localization/`.
2. Игровые ассеты, на которые **реально ссылается** сцена или скрипт (`assets/…`), плюс одна лицензия/README на набор.
3. Невосстановимые исходники ассетов: `.blend`, исходный рисунок персонажа, скрипт сборки ассета.
4. Короткие документы: правила, решения владельца, дизайн-документ, карточка **текущей** задачи.
5. Тесты `validate_*`, которые реально запускаются при проверке.

Всё остальное — **не в Git**.

### 2. Что хранить только локально — в `local/` (папка в `.gitignore`)

- снимки экрана ПК/телефона, «до/после», серии кадров, контактные листы, GIF, видео, записи микса;
- логи, JSON с результатами проверок (`checks.json`, `qa.json`, `metrics.json`, `browser-checks.json` и подобные), SHA/хеши сборок;
- PDF/HTML-экспорты, автономные галереи, одно и то же изображение в нескольких размерах;
- промежуточные и невыбранные варианты рисунков/концептов/раскладок (в Git остаётся только выбранный, если он нужен игре);
- APK и другие сборки, бэкапы, задания и ответы Ollama.

Раскладка: `local/qa/<задача>/`, `local/previews/<задача>/`, `local/exports/`, `local/builds/`. Показать владельцу картинку = прислать её в чат или назвать путь в `local/`, а не коммитить.

### 3. Лимиты на одну задачу/PR

- Новые файлы вне `assets/`, `scripts/`, `scenes/`, `localization/`, `art/blender/` — не больше **двух `.md`**. Картинок в `docs/` не добавлять.
- Протокол проверки — раздел в описании PR или один `.md` до **150 строк** без картинок: что проверено, где (ПК/S23), версия, итог, открытые вопросы.
- Бинарный файл больше **2 МБ** — только игровой ассет, с причиной в описании PR.
- Сначала дописать абзац в существующий документ, новый файл — только если без него нельзя. Не копировать один отчёт в MEMORY, STATUS, README и docs/README.
- `MEMORY.md` — не больше 120 строк. `STATUS.md` — только текущее состояние и очередь, не больше 200 строк; закрытые протоколы не переносить в архив, а удалять (история есть в `git log` и PR).

### 4. Перед каждым коммитом — обязательно

- **Никогда** `git add -A`, `git add .`, `git add docs/`, `git add art/`. Только явные пути к файлам задачи.
- Выполнить и прочитать:
  ```
  git status --short
  git diff --cached --stat
  git diff --cached --name-only --diff-filter=A
  ```
- Каждый новый файл должен подходить под пункт 1. Снимки/логи/отчёты: `git restore --staged <файл>` и перенести в `local/`.
- В описании PR — строка «Новые файлы: N, из них бинарных: M» и одна фраза, зачем каждый бинарный.
- PR, где больше половины новых файлов — картинки/отчёты, считается неготовым, даже если все тесты зелёные.

### 5. Уже закоммиченное

Существующие `art/previews/`, `docs/art/reviews/`, `docs/art/cons-01/images/`, QA-JSON и PDF убираются отдельной задачей **FILES-CLEANUP-01**: (1) скопировать в `local/`, (2) `git rm -r --cached <папки>`, (3) PR. Историю Git (`filter-repo`, `push --force`) не переписывать без отдельного явного согласия владельца.

### 6. Исключение

Файл вне пункта 1 попадает в Git, только если владелец прямо сказал про **этот** файл: «положи в Git».

## Непрерывная работа и очередь согласования — поручение владельца 28 сентября 2026

- Ожидание владельца останавливает только задачу, которой действительно нужно его решение, и зависящие от него шаги. Если есть независимая разрешённая работа, продолжать её без повторного разрешения: исправления, механики по текущему плану, анализ, подготовка арта, лор и задания.
- Результат, требующий личной оценки или решения, сохранять в отдельной ветке и **открытом PR в dev** с пометкой «На проверку владельцу». В описании: что изменено; где и как посмотреть/проверить; фактические проверки и ограничения; отдельный короткий список решений «принять / изменить / отклонить». Непроверенную или незавершённую реализацию обозначать как draft. Не сливать требующий согласования PR до ответа и не выдавать ожидание за завершение задачи.
- После сохранения такого результата записать PR и зависимость в текущую очередь и перейти к следующей независимой задаче от актуального dev в отдельной ветке/подходящем свободном worktree. Не строить новую обязательную зависимость на непринятом PR, не включать его изменения в соседнюю фичу. Одна активная реализация на исполнителя; открытые PR в ожидании оценки не занимают эту очередь. Это явное исключение к прежнему требованию начинать следующую карточку только после слияния предыдущей.
- Лор, персонажей, подводки, диалоги и приключения разрешено разрабатывать самостоятельными главами в отдельных PR. Каждая глава — связное проверяемое предложение с опорой на принятый канон, мотивацией участников, ходом задания, выборами/последствиями и нужными механиками. Помечать «Предложение, не канон, в игру не подключено». Имена и спорные решения оставлять рабочими; новые главы не требуют принятия предыдущих, если их можно написать независимо. Разрешение писать предложения не разрешает автоматически менять канон, планировку или внедрять новые системы.
- **Уточнение владельца 29 сентября — обсуждение сюжетов:** главы #141, #142 и #148 уже сохранены в dev, но владельцем **не согласованы**. Вернуться к ним для отдельного обсуждения в чате, по одной главе: краткий пересказ, мотивация персонажей, выборы/последствия и несколько конкретных вопросов; затем правки и явное решение по названной редакции. Слияние PR и общее поручение «закрыть готовые PR» не заменяют такое решение. Эти главы остаются в очереди согласования до обсуждения, в игру их не подключать. Для новых сюжетных предложений сохраняется правило открытого PR до ответа владельца; отдельный PR с процедурным уточнением не означает принятие сюжета.
- Продолжение означает содержательный законченный результат, а не бесконечное размножение вариантов и PR. Не дублировать уже предложенные главы, не прятать дефекты за переключением задачи. Отказ владельца закрывает/перерабатывает соответствующее предложение, не откатывая независимую работу. D-080 и требования качества/проверок сохраняются. Нехватку доступа, лимиты и отсутствие исполняющего агента сообщать прямо; файл в очереди не означает фоновую работу.

## Совместная работа и ответственность за вид сцены — поручение владельца 28 сентября 2026

- **Codex отвечает за визуальную целостность результата в игре:** композицию, архитектуру и назначение зданий, размещение, масштаб, материалы, свет, растительность и детали. Он готовит визуальные ориентиры, проверяет интеграцию исполнителя (в том числе Claude) и возвращает конкретные дефекты на исправление. Проверка отдельной модели не означает приёмку окружающего участка.
- Перед работой агенты согласуют текущую задачу, владельца изменяемых файлов и точку передачи. Не править одни игровые файлы одновременно. Исполнитель передаёт Codex точный коммит/состояние файлов, реальные игровые кадры, путь к сборке и известные ограничения; Codex отвечает результатом проверки. Файл в очереди моста и квитанция доставки не означают, что другой агент прочитал поручение, работает или согласился: нужно его явное подтверждение. Ожидание/недоступность сообщать владельцу честно.
- **Расстановка должна быть осмысленной и проверенной по фактическим габаритам.** Проверять весь объём здания, крышу, крыльцо, ступени, реквизит и коллизии относительно дороги, соседей, воды и рельефа. Дома и поля не перекрывают проезжую часть; входы имеют свободный сухой подход; основания и предметы стоят на опорах. Колёса и другие механизмы связаны с работающим зданием. Не маскировать ошибку случайной пристройкой, смещением камеры или общим изменением света.
- Перед передачей визуального изменения владельцу Codex осматривает **весь затронутый маршрут и соседние объекты** из обычной игровой камеры, в движении: подход по дороге, внешний вид с нескольких сторон, вход/выход, проходы и берег. Проверять ясный день и относящиеся к изменению дождь/ночь; для материалов сохранять одинаковые условия сравнения. Сверять результат с принятой опорой и учитывать стоимость на телефоне. Эскизы, вид сверху, headless-тесты и сообщение исполнителя не заменяют этот осмотр.
- Найденные пересечения, зависшие предметы, заблокированные подходы и несогласованный внешний вид исправлять и повторно проверять **до объявления готовности и просьбы об обычной приёмке**. Если показывается незавершённый вариант для обсуждения — прямо назвать его черновиком и перечислить дефекты. Не перекладывать обнаружение очевидных ошибок на владельца. Проверки ПК, актуальной APK, FPS и личная оценка владельца фиксируются отдельно.
- Эти правила обязательны для Codex и Claude; `CLAUDE.md` подключает этот файл как общую опору. Они не отменяют D-080, согласование новой планировки по D-064, распределение реализации по D-047 и окончательную художественную оценку владельца.

## Распределение работы — уточнение владельца 23 сентября 2026, D-047

- Прежнее требование «весь игровой код обязательно через Qwen» заменено выбором исполнителя по сложности. **Qwen через локальную Ollama — простые ограниченные изменения; Codex — сложный ввод, взаимодействие нескольких систем и трудные исправления**, включая нужные GDScript и сцены Godot. Это уже разрешено владельцем, повторного согласования прямой работы Codex в этих границах не требуется.
- Простая задача имеет ясный локальный контракт: однотипная правка данных, параметров или небольшой изолированной функции без сложных связей состояний. Небольшое число строк само по себе не делает задачу простой. Владение жестами/фокус/пауза, согласование ввода с UI/камерой/боем, сохранения и переходы нескольких систем ведёт Codex. Исполнитель и причина выбора записываются в карточке до реализации.
- Codex также координирует, готовит поручения Qwen, настраивает подключения, читает фактический diff и отвечает за итог. Передачу трудного исправления от Qwen к Codex явно отмечать в карточке/протоколе; не приписывать собственные изменения локальной модели.
- **Основные тесты готовит, пишет/исправляет и запускает сам Codex**, независимо от автора реализации. Не отдавать ключевые проверки Qwen и не считать её самопроверку приёмкой. Ожидания проверок следуют требованиям, а не повторяют реализацию; сохраняются необходимые проверки ПК и актуальной установленной APK на телефоне.
- При дефекте Qwen дать один ограниченный возврат с воспроизведением. Если после него результат снова неприемлем, пересмотреть причину и передать сложную часть Codex, сохранив пригодный diff; не продолжать серию мелких перепоручений. Ошибку теста исправляет Codex, не ослабляя ожидаемое поведение. Нехватка контекста/лимит правок — отдельно диагностируемый сбой постановки или инструмента, не доказательство неспособности модели.
- Если Ollama недоступна или ей не хватает возможности, сообщить конкретную причину. Для уже разрешённой сложной работы Codex локальная модель не является обязательной зависимостью. Правило не разрешает автоматически скачивать другую модель, менять провайдера Ollama или передавать реализацию облачным субагентам.
- Использовать установленную локальную модель. Не выбирать облачный вариант Ollama и не скачивать другую модель без согласования.
- Правила и документацию, конфигурацию инструментов и средства подключения Codex может настраивать в рамках запрошенной задачи.
- Если ты сам запущен как локальная модель Ollama, ты и есть исполнитель: выполняй порученную задачу и не делегируй её повторно.
- Создание 3D-геометрии и скриптов Blender также поручать локальной модели; Codex читает полученные скрипты, запускает Blender и проверяет экспорт в Godot.

## Делегирование локальной модели

- Исполнитель простых делегированных задач: `qwen3.8-24k:latest`, локальный Ollama на `http://127.0.0.1:11434`. Сложные задачи Codex ведёт напрямую согласно D-047.
- Для анализа: `node tools/ollama-godot.mjs --task-file ПУТЬ_К_ЗАДАНИЮ`.
- Для порученной реализации добавить `--write`: `node tools/ollama-godot.mjs --task-file ПУТЬ_К_ЗАДАНИЮ --write`.
- Передавай задание в UTF-8 файле, например в `.tools/ollama-godot/tasks/`, с целью, разрешёнными файлами и критериями проверки. Не формируй shell-команду из ответа модели.
- Модель может читать файлы, писать игровой код и сцены, а также вызывать Godot MCP для создания и изменения сцен. Проект ограничен папкой AshBound; прямых команд оболочки и Git у модели нет.
- Логи реальных ответов и вызовов инструментов: `.tools/ollama-godot/runs/`. Оригиналы изменённых файлов сохраняются там же в `backups/`.
- После задачи проверяй фактический diff и результат Godot; ответ модели сам по себе не подтверждает готовность.
- Для Blender добавить `--blender-scripts`: разрешена запись `.py` только в `art/blender/`. `--image ПУТЬ` передаёт локальной модели PNG/JPEG из проекта. Для длинных скриптов с изображением использовать `--context 24576 --output-tokens 8192`; обрезанный ответ не выполнять. Когда нужно только написать файлы, добавить `--files-only`, чтобы не запускать Godot MCP. Не включать `--think` без отдельной причины: в проверенной задаче этот режим исчерпал ответ рассуждениями без результата.

## Перед задачей и её завершение

- Работаем локально на ПК владельца (Windows), общаемся по-русски. Перед задачей читать [MEMORY](MEMORY.md), [оглавление документов](docs/README.md), [STATUS](docs/production/STATUS.md). Текущий порядок — STATUS, этапы и критерии — [ROADMAP](docs/production/ROADMAP.md), решения — [DECISIONS](docs/production/DECISIONS.md). Старые отчёты и архивы не являются новыми поручениями; прямое указание владельца имеет приоритет.
- Перед реализацией заполнить [карточку](docs/production/TASK_TEMPLATE.md): один проверяемый результат, основание и зависимости, исходный коммит, разрешённые файлы, границы, реальные интерфейсы, исполнитель с причиной выбора, критерии и способ проверки. Одна активная реализация на исполнителя; переход между задачами — по разделу непрерывной работы выше.
- Поручение Ollama получает свежий ограниченный контекст из текущего исходника, точные сигнатуры и опорные файлы. Не заменять их историей чата и не принимать выдуманные API. Возврат включает воспроизведение, ожидаемое/фактическое поведение и границы исправления; порядок повторного возврата — D-047 выше.
- Изменение объёма/порядка сначала записать в STATUS с причиной и затронутой задачей. Идеи вне этапа — в очередь. До выхода из [CONS](docs/production/CONSOLIDATION_PLAN.md) по записанным критериям новые системы/расширение контента приостановлены, кроме прямо разрешённых последующих поручений владельца. Такие исключения не закрывают остальные зависимости CONS; общее «продолжаем» не расширяет их границы. Не откатывать Git, удалять работающие механики или переписывать проект ради «порядка».
- После задачи обновлять краткие состояние/проверку в STATUS, новые подтверждённые решения — в MEMORY/DECISIONS. MEMORY хранит устойчивый контекст, STATUS — очередь, ROADMAP — этапы; историю оставлять в Git/PR. Не дублировать длинный отчёт и устаревшие «следующие шаги» по документам.

## Проверка результата и устройства

- Codex читает фактический diff, сам выбирает обычные/граничные сценарии, отказы и относящиеся регрессии. Проверка работы Qwen независимая; свой код Codex проверяет отдельным проходом QA, не называя его внешним ревью. Ошибку теста исправлять по требованиям, не ослаблять ожидания ради PASS.
- В Godot проверять завершение всех сценариев, ожидаемый результат, код выхода и весь журнал. Выход 0 или маркер PASS при SCRIPT ERROR/ошибке движка не означает успех. Само сообщение исполнителя не подтверждает готовность.
- Проверять целый маршрут текущего объёма: вход, движение, встречу, подготовку/атаку/защиту, реакцию и выход. Стенд не выдавать за интеграцию в кампанию; не добавлять незаказанные механики ради «закрытия» сценария. Визуальная приёмка всего участка — по обязательному разделу выше.
- Подтверждённые платформы — ПК и Android; устройства владельца — Samsung S23 и OnePlus 13T. Версию, платформу, журналы/кадры, ограничения и личную оценку фиксировать отдельно. Наличие устройства и старый тест не подтверждают новую проверку.
- Основная сцена — `scenes/world/world.tscn` (D-095); двор `first_courtyard.tscn` остаётся стендом боя/инвентаря, его проверки не равны проверке мира.
- Для ручной проверки на ПК запускать доступную сцену отдельным видимым окном и сообщать управление. Сохранять несохранённые сцены редактора; не закрывать/перезапускать чужие окна и не прерывать ручную игру новой сборкой. Запуск не означает принятие.
- Перед просьбой проверить телефон установить и сверить актуальную APK, открыть нужную сцену; ПК не заменяет телефон. После передачи владельцу автоматические касания прекращаются; после его сообщения об окончании теста можно продолжать собственную проверку. Новое поручение обновить/проверить телефон разрешает продолжение, старый ручной тест не является бессрочным запретом. Учитывать текущие ограничения владельца на устройство.
- Для документации/анализа проверять содержание, ссылки и согласованность; новую APK не собирать. Не обещать проверку неустановленной версии или готовность обеих платформ по старым данным.

## Ветки и слияние

- Фичи, исправления, правила и документы — отдельная новая ветка от актуального `dev`, обычно `codex/<название>`. Перед переключением проверить Git, сохранить чужие изменения; завершённую ветку не переиспользовать. В `dev`/`main` непосредственно не разрабатывать.
- После чтения diff и нужных проверок отправить ветку, создать PR в удалённую `dev`. Проверить точный коммит, конфликты и обязательные проверки; после разрешения конфликтов повторить затронутые сценарии. Интеграция — через GitHub PR, не локальное слияние с прямым push в `dev`.
- Проверенные PR без обязательного личного решения можно сливать автономно: это уже разрешено владельцем. Не запрашивать повторное разрешение на публикацию/PR/обычное слияние. Требующий оценки результат остаётся открытым по правилам выше; необходимое решение ждать по конкретному результату, молчание не считать ответом.
- После GitHub-слияния обновить локальную `dev` без переписывания истории и проверить включение коммитов. Удалять локально/на GitHub только завершённые ветки, сохранённые в `dev`, без активной работы/PR; сохранять `dev`, `main` и неслитые изменения. При занятом checkout использовать свободный worktree.
- В `main` переносить подготовленное состояние `dev` только как проверенный играбельный промежуточный билд: состав/версия, путь или способ запуска, пройденный маршрут, платформы и ограничения. Документы, отдельная модель, незавершённый прототип и отдельная фича не равны такому билду.

## Мир, рисунки и интерфейс

- **D-064:** перед новой игровой планировкой — [концепт → согласование конкретной версии → план → реализация](docs/production/WORLD_CONCEPT_WORKFLOW.md). Показать схему (Watabou/другой предложенный владельцем инструмент по назначению), сохранить экспорт в `local/` по D-080, обсудить нюансы. Существенное отклонение снова показать. Общее «дальше», подключённый телефон и технический PASS не заменяют решение. Непринятая проба `codex/starter-forest-graybox/7107ea0` не разрешена к автослиянию; актуальные принятые зоны и порядок — STATUS/DECISIONS.
- Перед визуальной работой читать [STYLE_REFERENCE](docs/art/STYLE_REFERENCE.md), передавать конкретные исходники/эталоны, сохранять палитру, контур, масштаб, материалы, свет, UI и язык эффектов. Начальная страница источников не заменяет готовое сравнение CONS-01. Новый рисунок сначала сравнить с существующим в нужных действиях/ракурсах, затем подключать. Принятая [опора света/цвета деревни](docs/art/VILLAGE_LOOK_REFERENCE.md) сохраняется; деревья не заменять ради сторонних моделей (D-090).
- Окружение 3D, герой/NPC визуально 2D; плавный мир и редкая смена цельных рисованных поз ([VISUAL_DIRECTION](docs/art/VISUAL_DIRECTION.md), [ANIMATION_PIPELINE](docs/art/ANIMATION_PIPELINE.md)). Blender-кукла/SIDE-GAIT-02 из частей отвергнуты, не возвращать их. Обе половины шага и постоянные пропорции обязательны. 60/15 FPS — ориентир, не ограничение движка/ввода; D-088: желательно 60 на устройствах уровня S23, допустимо 30–40 на старом железе, нужны настройки густоты/дальности/выключения травы.
- Камера — перспективное третье лицо из-за спины, ориентир оригинальная Gothic: обзор вокруг героя, движение относительно камеры, плоскости героя/NPC обращены к камере; рисованные ракурсы выбираются относительно неё. Изометрический/высокий боковой вид отвергнут. Перед изменениями читать [THIRD_PERSON_SPRITES](docs/levels/THIRD_PERSON_SPRITES.md).
- **D-079/059:** один герой с [принятой внешностью](art/characters/accepted-traveler-v1/README.md); редактор внешности/парикмахер/выбор пола и черт исключены, не создавать поля UI/сохранений или варианты. NPC этим не унифицируются. Возврат кастомизации — только по прямому новому решению. Перед персонажами/сетами читать [рецепт 2.0](docs/art/ARMOR_ANIMATION_PLAYBOOK.md), [CHARACTER_VARIANTS](docs/art/CHARACTER_VARIANTS.md) и [границы фиксированного героя](docs/production/FIXED_PROTAGONIST_TASK.md).
- Сохранять цельные рисунки героя/комплекта/оружия, исходники/SHA, порядок фаз, общие преобразования, конечные pixel_size и опору ног. Не смешивать головы/торсы, не нормализовать каждый кадр по bbox, не компенсировать масштаб дважды, не накладывать аксессуар поверх тела. Генерация недетерминирована; точное воспроизведение — из сохранённых RGBA и сборщиков. Сеты/оружие сохраняют идентичность героя. Новый сет: normal/slow, idle/walk/run во всех ракурсах и свежая APK, затем личная оценка. Принятый бег не менять без нового поручения владельца; позы блока/попадания уже есть в первой локации (D-094).
- Перед любым UI читать [книгу](docs/art/ui/README.md), [tokens](docs/art/ui/tokens.json) и соответствующие PDF/HTML-образцы (экспорты локально, D-080). Опора должна работать локально без сервера. В карточке указать версию книги и роли параметров. Использовать общий `assets/ui/ashbound_ui.tres`, не копировать палитру; шрифты/размеры/цвета менять через обновление опоры с причиной и сравнением. Существенное направление обсуждать на образце. Действия: «Блок», «Удар», «Бег» / Block, Attack, Run; без произвольного верхнего регистра, клавиши/сокращения сохраняются.
- Игра EN/RU на обеих платформах, одинаковый объём текста. Перед UI/диалогами/квестами/предметами читать [LOCALIZATION](docs/architecture/LOCALIZATION.md): стабильные ключи и отдельные каталоги, переводы не становятся ID/данными сохранений, новые тексты готовить и проверять на обоих языках. Русский исходный лор и общение сохраняются; двуязычная озвучка отдельно не заказана.
- Язык относится к приложению: отдельная верхняя вкладка «Настройки» общего меню, крупные варианты «Язык устройства»/English/Русский, выбранный вариант и сохранение. Не возвращать маленький список языка внутри инвентаря или отдельную кнопку языка в HUD. Новые настройки добавлять по реализации, без неработающих элементов.
