# Правила работы над AshBound

## Распределение работы

- Локальный код проекта, GDScript, игровые механики, создание и изменение сцен Godot выполняет локальная LLM через Ollama. Это явное требование владельца проекта.
- Codex выполняет координацию: уточняет задачи, готовит задания локальной модели, настраивает подключения, читает и проверяет результат, запускает проверки и сообщает об ошибках.
- Исправления игрового кода и сцен также поручать Ollama. Codex не должен незаметно подменять локальную модель собственной реализацией.
- Если Ollama недоступна, модель не справляется или отсутствует нужная возможность, сообщить конкретную проблему. Не переходить на облачную модель для реализации без явного разрешения пользователя.
- Использовать установленную локальную модель. Не выбирать облачный вариант Ollama и не скачивать другую модель без согласования.
- Правила и документацию, конфигурацию инструментов и средства подключения Codex может настраивать в рамках запрошенной задачи.
- Если ты сам запущен как локальная модель Ollama, ты и есть исполнитель: выполняй порученную задачу и не делегируй её повторно.
- Создание 3D-геометрии и скриптов Blender также поручать локальной модели; Codex читает полученные скрипты, запускает Blender и проверяет экспорт в Godot.

## Проверка результатов

- Перед изменениями проверить состояние Git и сохранить существующие изменения пользователя.
- Поручать локальной модели ограниченные задачи с конкретными файлами и критериями готовности.
- После выполнения прочитать изменения, проверить сцены/скрипты средствами Godot и сообщить фактический результат. Само сообщение модели об успехе не считается проверкой.
- Владелец разрешил автономно выполнять задачи текущего плана, публиковать проверенные ветки, создавать PR в `dev`, сливать их после успешной проверки и удалять завершённые ветки. Не просить повторное разрешение на эти шаги. Для критического решения или необходимой личной проверки владельца сформулировать конкретный запрос и дождаться ответа; не считать отсутствие ответом.

## Ветки и слияние

- Рабочая интеграционная ветка проекта — `dev`. Каждую новую фичу разрабатывать в отдельной новой ветке от актуального `dev`, по умолчанию `codex/<название-фичи>`. Законченную ветку не использовать для следующей фичи.
- Исправления, изменения правил и документации также оформлять отдельными тематическими ветками. Не вести разработку и не коммитить её непосредственно в `dev` или `main`.
- Перед созданием ветки проверить состояние Git и актуальность `dev`, сохранить существующие незакоммиченные изменения. Не терять чужие изменения и не перезаписывать историю ради переключения ветки.
- После реализации прочитать фактические изменения, выполнить проверки, соответствующие задаче, исправить обнаруженные проблемы, отправить ветку и создать PR в удалённую `dev`. Проверить точный коммит PR, отсутствие конфликтов и требуемые проверки; затем слить через GitHub. Не сливать локально и не пушить `dev` до PR. После конфликта повторно проверить затронутое поведение; непроверенная работа не готова к слиянию.
- Для игровых изменений проверять относящиеся к ним сценарии Godot и целевые платформы по плану; для изменений только документации проверять содержание, согласованность правил и ссылки. В записи задачи сохранять фактический результат проверки.
- `main` обновлять только при готовности определённого проверенного играбельного билда как промежуточного итога. Переносить в неё подготовленное состояние `dev`; отдельные фичи, текущие правки документов и незаконченные прототипы напрямую в `main` не отправлять.
- Для такого билда записать состав и версию, путь к сборке или способ запуска, пройденный игровой сценарий, проверенные платформы и известные ограничения. Готовность документов или просмотр отдельных моделей сами по себе не означают готовность играбельного билда.
- После GitHub-слияния обновить локальную `dev` без переписывания истории, проверить включение коммитов и удалить завершённую ветку локально и на GitHub. Следующую фичу начинать новой веткой от обновлённой `dev`. Удалять только ветки, чьи изменения уже сохранены в `dev`, без активной работы/PR; сохранять `dev`, `main` и неслитые изменения. Само разрешение удалять мусорные ветки не разрешает удалять непроверенную работу.

## Подключения

- Репозиторий: `https://github.com/AlekseyChist/ashbound.git`.
- Godot MCP зарегистрирован в Codex под именем `godot`.
- Машинные пути и состояние настройки описаны в `GODOT_CONNECTION.md`.

## Делегирование локальной модели

- Основной исполнитель: `qwen3.8-24k:latest`, локальный Ollama на `http://127.0.0.1:11434`.
- Для анализа: `node tools/ollama-godot.mjs --task-file ПУТЬ_К_ЗАДАНИЮ`.
- Для порученной реализации добавить `--write`: `node tools/ollama-godot.mjs --task-file ПУТЬ_К_ЗАДАНИЮ --write`.
- Передавай задание в UTF-8 файле, например в `.tools/ollama-godot/tasks/`, с целью, разрешёнными файлами и критериями проверки. Не формируй shell-команду из ответа модели.
- Модель может читать файлы, писать игровой код и сцены, а также вызывать Godot MCP для создания и изменения сцен. Проект ограничен папкой AshBound; прямых команд оболочки и Git у модели нет.
- Логи реальных ответов и вызовов инструментов: `.tools/ollama-godot/runs/`. Оригиналы изменённых файлов сохраняются там же в `backups/`.
- После задачи проверяй фактический diff и результат Godot; ответ модели сам по себе не подтверждает готовность.
- Для Blender добавить `--blender-scripts`: разрешена запись `.py` только в `art/blender/`. `--image ПУТЬ` передаёт локальной модели PNG/JPEG из проекта. Для длинных скриптов с изображением использовать `--context 24576 --output-tokens 8192`; обрезанный ответ не выполнять. Когда нужно только написать файлы, добавить `--files-only`, чтобы не запускать Godot MCP. Не включать `--think` без отдельной причины: в проверенной задаче этот режим исчерпал ответ рассуждениями без результата.

## Работа по плану разработки

- Перед новой задачей читать `MEMORY.md`, `docs/README.md` и `docs/production/STATUS.md`; порядок этапов и критерии завершения находятся в `docs/production/ROADMAP.md`. `MEMORY.md` — сохраняемый в Git краткий контекст проекта; обновлять его при новых подтверждённых решениях.
- Сюжетная основа и первый эпизод находятся в `docs/narrative/`. Исходный лор владельца сохранён без изменений в `LORE_ORIGINAL.txt`; новые предложения не считать утверждённым каноном без решения владельца.
- Уточнение владельца о темпе истории: начало посвящено освоению жизни, местности, боя и местным заданиям; встреча с древней расой происходит значительно позже. Не возвращать раннее раскрытие угрозы и снятую историю о разбираемых защитных узлах из черновика v0.1.
- Подтверждённые платформы — ПК и Android с начала разработки. Устройства владельца для проверок — Samsung S23 и OnePlus 13T; наличие устройств не означает, что тестирование на них уже выполнено.
- Художественная основа: окружение 3D, герой и NPC визуально 2D, с анимациями и видимой сменой одежды/оружия. Плавный мир сочетается с редкой сменой поз персонажей в духе старой мультипликации; 60/15 FPS — условный ориентир, не ограничение всей игры. Перед работой с персонажами читать `docs/art/VISUAL_DIRECTION.md`; не подменять этот стиль обычными плавно анимированными 3D-персонажами.
- Камера — перспективное третье лицо из-за спины героя, ориентир владельца — оригинальная Gothic. Обзор вращается вокруг героя, движение учитывает камеру; плоскости 2D-героя и NPC поворачиваются к ней. Высокий боковой/изометрический вид первого прототипа отвергнут. Ракурсы рисованных персонажей выбираются относительно камеры; см. `docs/levels/THIRD_PERSON_SPRITES.md`.
- После завершённой задачи обновлять состояние и фактическую проверку в `STATUS.md`. Идеи вне текущего этапа записывать в очередь, не расширять реализацию без причины. Прямые новые указания владельца имеют приоритет над записанным планом.
- Перед проектированием боя и боевых анимаций читать `docs/design/COMBAT_MASTERY.md`: нужны три различимые степени техники для каждого направления боя, включая оружие и магию. Окна идеального блока/уклонения пока являются предложением для прототипирования, а не реализованным или окончательно сбалансированным правилом. Редкая смена 2D-поз не должна снижать отзывчивость ввода.
- Перед изменениями внешности, ремёсел, профессий, собственности и торговли читать `docs/design/LIFE_AND_ECONOMY.md`; перед дверями и взломом — `docs/design/INTERIORS_AND_ACCESS.md`. Специальные знания требуют обучения, качество предмета не равно навыку героя. Предусмотрены самостоятельная бытовая жизнь, доход вне игры, вход в каждый дом и отдельный бег; наличие записи в плане не означает готовую систему.
- Правила времени, восстановления леса и позднего вторжения находятся в `docs/design/WORLD_TIME.md`. Исход бездействия задан владельцем, но численные сроки и ход угрозы вне игры ещё не утверждены. Не превращать проектные варианты в скрытый действующий таймер и не переносить древних в начальное обучение. Реализовывать часы и экономические начисления с проверкой сохранений и отсутствия повторного расчёта.
