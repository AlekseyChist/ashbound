# Правила работы над AshBound

## Распределение работы

- Локальный код проекта, GDScript, игровые механики, создание и изменение сцен Godot выполняет локальная LLM через Ollama. Это явное требование владельца проекта.
- Codex выполняет координацию: уточняет задачи, готовит задания локальной модели, настраивает подключения, читает и проверяет результат, запускает проверки и сообщает об ошибках.
- Исправления игрового кода и сцен также поручать Ollama. Codex не должен незаметно подменять локальную модель собственной реализацией.
- Если Ollama недоступна, модель не справляется или отсутствует нужная возможность, сообщить конкретную проблему. Не переходить на облачную модель для реализации без явного разрешения пользователя.
- Использовать установленную локальную модель. Не выбирать облачный вариант Ollama и не скачивать другую модель без согласования.
- Правила и документацию, конфигурацию инструментов и средства подключения Codex может настраивать в рамках запрошенной задачи.
- Если ты сам запущен как локальная модель Ollama, ты и есть исполнитель: выполняй порученную задачу и не делегируй её повторно.
- Создание 3D-геометрии и скриптов Blender также поручать локальной модели; Codex читает полученные скрипты, запускает Blender и проверяет экспорт в Godot.

## Проверка результатов

- Перед изменениями проверить состояние Git и сохранить существующие изменения пользователя.
- Поручать локальной модели ограниченные задачи с конкретными файлами и критериями готовности.
- После выполнения прочитать изменения, проверить сцены/скрипты средствами Godot и сообщить фактический результат. Само сообщение модели об успехе не считается проверкой.
- Отправку изменений в GitHub выполнять по указанию пользователя.

## Подключения

- Репозиторий: `https://github.com/AlekseyChist/ashbound.git`.
- Godot MCP зарегистрирован в Codex под именем `godot`.
- Машинные пути и состояние настройки описаны в `GODOT_CONNECTION.md`.

## Делегирование локальной модели

- Основной исполнитель: `qwen3.8-24k:latest`, локальный Ollama на `http://127.0.0.1:11434`.
- Для анализа: `node tools/ollama-godot.mjs --task-file ПУТЬ_К_ЗАДАНИЮ`.
- Для порученной реализации добавить `--write`: `node tools/ollama-godot.mjs --task-file ПУТЬ_К_ЗАДАНИЮ --write`.
- Передавай задание в UTF-8 файле, например в `.tools/ollama-godot/tasks/`, с целью, разрешёнными файлами и критериями проверки. Не формируй shell-команду из ответа модели.
- Модель может читать файлы, писать игровой код и сцены, а также вызывать Godot MCP для создания и изменения сцен. Проект ограничен папкой AshBound; прямых команд оболочки и Git у модели нет.
- Логи реальных ответов и вызовов инструментов: `.tools/ollama-godot/runs/`. Оригиналы изменённых файлов сохраняются там же в `backups/`.
- После задачи проверяй фактический diff и результат Godot; ответ модели сам по себе не подтверждает готовность.
- Для Blender добавить `--blender-scripts`: разрешена запись `.py` только в `art/blender/`. `--image ПУТЬ` передаёт локальной модели PNG/JPEG из проекта. Для длинных скриптов с изображением использовать `--context 24576 --output-tokens 8192`; обрезанный ответ не выполнять. Когда нужно только написать файлы, добавить `--files-only`, чтобы не запускать Godot MCP. Не включать `--think` без отдельной причины: в проверенной задаче этот режим исчерпал ответ рассуждениями без результата.

## Работа по плану разработки

- Перед новой задачей читать `MEMORY.md`, `docs/README.md` и `docs/production/STATUS.md`; порядок этапов и критерии завершения находятся в `docs/production/ROADMAP.md`. `MEMORY.md` — сохраняемый в Git краткий контекст проекта; обновлять его при новых подтверждённых решениях.
- Сюжетная основа и первый эпизод находятся в `docs/narrative/`. Исходный лор владельца сохранён без изменений в `LORE_ORIGINAL.txt`; новые предложения не считать утверждённым каноном без решения владельца.
- Подтверждённые платформы — ПК и Android с начала разработки. Устройства владельца для проверок — Samsung S23 и OnePlus 13T; наличие устройств не означает, что тестирование на них уже выполнено.
- После завершённой задачи обновлять состояние и фактическую проверку в `STATUS.md`. Идеи вне текущего этапа записывать в очередь, не расширять реализацию без причины. Прямые новые указания владельца имеют приоритет над записанным планом.
